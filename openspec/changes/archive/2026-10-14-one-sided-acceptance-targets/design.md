# Design

## Context

See proposal.md (Why). Current state, verified against the code:

- **Two readers, two rules.** `study/targets.py::_evaluate_type_i` and `_evaluate_specificity` compute
  `bound = se_tolerance · summary.monte_carlo_se` and `met = |rate − α| ≤ bound`, where `monte_carlo_se` is
  the *empirical* binomial SE of the rate (`sqrt(rate(1 − rate)/R)`, zero at rate 0 or 1).
  `study/phase4.py::type_i_inflation_bound(alpha, k, n)` returns `α + k · sqrt(α(1 − α)/n)` and is the rule
  for every gate control (`mandatory_control`) and Type I inflation row, and for the anchor decision rule.
- **Observations are the report.** `write_target_report` writes `acceptance_report.json` as
  `asdict(TargetEvaluation)` and `acceptance_report.csv` with one `obs_<key>` column per observation key
  (union across rows, in first-appearance order). Twenty-six committed `acceptance_report.*` files under
  `results/` are regenerated by `scripts/motco_study.py report`; their observation keys are exactly
  `cell_id, phase, trajectory_mode, statistic, alpha_target, se_tolerance, rejection_rate, monte_carlo_se,
  available_replicates, deviation, bound` (+ `effect_size` on specificity rows).
- **Targets are not identity.** Acceptance targets enter neither cell ids nor parameter signatures
  (`tests/test_committed_config_identity.py` pins generator/evaluation only). `dump_study_config` serializes
  targets through `_dataclass_dict` (every field), and no dump is committed — dumps are test round-trips.
- **Import graph.** `targets.py` imports `config` and `spectrum`; `phase4.py` imports `config` only. A
  `targets → phase4` edge introduces no cycle.

## Goals / Non-Goals

**Goals:**
- One key, two target kinds, one shared formula with the gate.
- Byte identity of every default-form report, including CSV column sets.
- A config that opts in reads the same on disk as the gate rule it mirrors (`alpha`, `se_tolerance`).

**Non-Goals:**
- No change to the gate, the anchor/rank/design-point rules, or the power monotonicity target.
- No flip of the default; no edit to any committed config or committed `report/`.
- No lower-bound (`lower`) form: a control rejecting *more* than α is the only failure a control target
  exists to catch, and a power floor is already the power target's job.

## Decisions

### D1. The key is `bound`, with values `two_sided` | `upper`, on each target entry

Per-entry rather than a block-level switch so a config can hold a translation control to the upper bound
while leaving another target two-sided, matching how gate rules are declared per pair. The value names the
*form of the bound* rather than `one_sided`, because a one-sided test has a direction and `upper` states it.
Alternative considered: `sided: 1 | 2` — rejected as it does not name the direction. Alternative: a separate
`alpha_se: true` flag for the SE basis — rejected; the direction and the SE basis move together (the gate's
rule is the pair), and two flags would allow a two-sided α-based-SE form nobody has asked for.

### D2. `upper` reuses `phase4.type_i_inflation_bound` verbatim

The proposal's whole point is that the two readers agree; sharing the function makes "mirrors the gate" a
code fact rather than a documentation claim, and the gate's `Phase4SummaryError` on `n ≤ 0` cannot fire
because both evaluators already return `met=None` ("No available replicates") before computing a bound.
The `R` is `summary.available_replicates`, the same count the gate reads.

### D3. The dataclass field defaults to `"two_sided"`; the parser validates; the evaluator branches

`TypeIControlTarget.bound: str = "two_sided"` and the same on `SpecificityTarget`. `_build_type_i_target` /
`_build_specificity_target` read `raw.get("bound", "two_sided")` and raise `StudyConfigError` naming
`acceptance.type_i[i].bound` / `acceptance.specificity[i].bound` and the value when it is not one of the two
constants (module-level `_TARGET_BOUNDS = {"two_sided", "upper"}`). Validation lives in the builders, as the
existing `se_tolerance`/`alpha` checks do, not in `__post_init__`, so programmatic construction in tests stays
cheap. The evaluators branch once on `target.bound`; the two-sided branch is the existing code, untouched.

### D4. Observations under `upper`

The upper branch records, after the common keys:

| key | value |
|---|---|
| `bound_kind` | `"upper"` |
| `alpha_se` | `sqrt(α(1 − α)/R)` |
| `deviation` | `rate − α` (signed; negative is conservative) |
| `bound` | `α + k · alpha_se` (the limit the rate is compared with) |

and the rationale reads `rate = 0.0240 <= alpha + 2.00·SE_alpha (0.0695)` (or `>`). `deviation` and
`bound` keep their names so a mixed report has one column each; the signed `deviation` is the one place the
semantics differ from the two-sided row, and `bound_kind` is present on exactly the rows where that is so.
Alternative considered: always write `bound_kind: "two_sided"` — rejected, it adds a column/key to every
committed report and breaks the byte-identity requirement.

Because the CSV column set is the union of observation keys in first-appearance order, a report whose
targets are all default-form gains no column; a mixed report gains `obs_bound_kind` and `obs_alpha_se` with
blanks on the two-sided rows. The JSON is per-row, so mixed reports need no special handling.

### D5. Dump writes the resolved value

`dump_study_config` keeps using `_dataclass_dict`, so a dumped config carries `"bound": "two_sided"` on every
target. Omitting it would need a one-off exclusion in the dump path for no consumer: nothing committed is a
dump, and a dump is defined as the resolved configuration. Load → dump → load round-trips both values.

### D6. First adopter is the net-displacement power comparison, not a committed config

Setting `bound: "upper"` on an existing committed config would change the regenerated `acceptance_report.*`
of a committed `results/` tree, contradicting "reproducible as recorded". The roadmap entry for item 3
is updated to say its two configs set `bound: "upper"` on every control target; that is where the key
earns its keep.

## Risks / Trade-offs

- [A mixed report's `deviation` column holds absolute values on some rows and signed values on others] →
  `bound_kind` marks the signed rows; the README states the rule; every committed report is unmixed.
- [A reader of `acceptance_report.json` keys on the rationale text] → the two-sided rationale is unchanged
  character-for-character; the `upper` rationale is a new string on new rows only.
- [The byte-identity claim is asserted, not measured] → task 1 captures a pre-change
  `acceptance_report.*` from a tiny end-to-end study (`tests/test_study_end_to_end.py` already builds one)
  and a test compares the post-change bytes; additionally the implementer re-runs
  `scripts/motco_study.py report` on the one committed results tree whose `merged.jsonl` is in the repo
  (`results/latent-spectrum-2026-09-02/`; its config declares no targets, so this only covers the
  empty-table case) and diffs `report/acceptance_report.*` against git. The trees with populated reports
  (`phase5-magnitude-2026-10-08`, `net-displacement-type-i-2026-10-13`) have their records only on `ing`;
  the in-repo end-to-end fixture is the binding check, and a diff on `ing` is optional confirmation.
- [Someone later flips the default] → that is a reporting change needing a recorded re-issue of every
  committed report, the same caveat the roadmap already attaches to the dispersion-materiality default
  (item 4); the README says so next to the key.

## Migration Plan

No migration: the key is additive and defaults to the current behavior. Rollback is removing the key from
any config that set it.
